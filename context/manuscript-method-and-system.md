## 3. The Mapa da Pesquisa method

### 3.1 Scope and methodological sequence

Mapa da Pesquisa is an operational method for constructing and revising a *prospective* research project. Its unit of analysis is a project plan rather than a completed study. Sergio's source map specifies a five-stage construction chain and an objective-to-method matrix; the later detailed specification adds explicit dependency, coherence and validation rules. For the scientific description, we expand those source components into seven analytical decisions: (M1) delimit a researchable problem from a briefing and available evidence; (M2) formulate a general objective that bears on the problem; (M3) decompose it into specific objectives; (M4) select literature topics and sources relevant to those objectives; (M5) organize where the objectives will be developed in the proposed work; (M6) state, for each objective, the material or data, collection procedure, analysis and expected intellectual output; and (M7) inspect the resulting relations and revise the plan when an upstream decision changes. M6 names the method matrix already in the original map, while M7 groups integration and revision behavior elaborated in the detailed specification and implementation. The order provides a default construction path, while revision may return to earlier decisions. A researcher's methodological judgment remains necessary to decide whether the proposed question, evidence and procedures are appropriate.

The method distinguishes three kinds of relation. An explicit link records that two particular project components were connected; a dependency rule states that a change to one *type* of component requires re-examination of downstream types; and a substantive methodological relation expresses a researcher's judgment that one component actually supports another. The implementation records the first and computes the second. It cannot establish the third from structure alone.

### 3.2 Project state and revision contract

We represent the current project as `P = (C, D, Q, E, R, H, A, W, v, s)`: canonical content `C`, editable drafts `D`, unaccepted generation proposals `Q`, explicit links `E`, references `R`, historical snapshots `H`, human review records `A`, workflow state `W`, persistence revision `v`, and source-context revision `s`. A project component has an identifier, type, proposed and/or approved content, references, source revision and validation status. `validated` records an accepted workflow decision; it does not certify scientific validity. `stale` requests re-examination after an upstream edit; it does not assert that the content is wrong.

The core revision contract is: preserve accepted content while drafting; reject confirmation of a draft based on an obsolete source context; on confirmation, compute downstream component *types* from the dependency graph and mark existing components of those types for review; record the decision and its history; and require a new human decision before a proposal becomes approved content. The type graph runs from prompt through problem candidate, problem statement, general objective, specific objectives, literature/development topics and methodological mapping to the final map. Chapter revisions additionally mark the methodological mapping stale because its rows refer to those topics. This is deliberately conservative type-level invalidation, not semantic impact analysis over individual links. It may produce unnecessary warnings and may miss dependencies outside its encoded graph.

### 3.3 Decision authority and validation

Validation has three distinct layers. Technical checks address schema, valid identifiers, allowed transitions, revision conflicts, persistence and recovery. Structural or heuristic checks signal such matters as missing coverage, invalid references, formulaic objectives and incomplete methodological rows; some are advisory and do not block progression. In particular, invoking a validation function is not equivalent to blocking route completion: definition and chapter handlers can turn academic messages into warnings, while the final-map handler uses advisory completion. Substantive appraisal asks whether the research design is coherent, feasible and properly evidenced. In this study, only Mario Reis and Sergio França perform that appraisal on the selected synthetic cases, independently before reconciliation. Their judgments are author assessments, not independent evidence of effectiveness for researchers generally. The source map specifies 3–6 specific objectives; the current generator's exactly four objectives are a narrower product default. The question-opening rule is also a local methodological/product convention, not a universal scientific requirement.

## 4. AI-assisted system implementing the method

### 4.1 Method-to-system correspondence

| Method decision | System operation | Inspectable implementation |
|---|---|---|
| M1 — problem delimitation | Interprets a briefing, gathers candidate sources, generates alternative problem candidates, and lets the researcher select and revise one. | `modules/research-workflow/discovery-service.ts`; `modules/generation/gemini.ts` (`generateProblemCandidates`); `app/api/projects/[id]/definition/route.ts` |
| M2–M3 — objective alignment | Generates editable general and specific objectives from accepted upstream context; applies definition checks before confirmation. | `modules/generation/gemini.ts` (`generateGeneralObjective`, `generateSpecificObjectives`); `modules/research-workflow/definition-validation.ts`; definition route |
| M4 — literature | Generates literature topics linked to objective IDs and available reference IDs; checks topic/reference relations. | `modules/generation/gemini.ts` (`generateLiteratureTopics`); `modules/research-workflow/chapter-validation.ts`; `app/api/projects/[id]/chapters/route.ts` |
| M5 — development structure | Generates development topics linked to objectives, including an explicit route for case-study introductions and final synthesis. | `modules/generation/gemini.ts` (`generateDevelopmentTopics`); chapter validation and route |
| M6 — operationalization | Produces a methodology matrix with a row for each specific objective and the general objective, then checks structure and warnings. | `modules/generation/gemini.ts` (`generateMethodologyPlan`); `modules/research-workflow/methodology-validation.ts`; `app/api/projects/[id]/methodology/route.ts` |
| M7 — integration and revision | Assembles a final graph, checks coherence, separates proposals/drafts from accepted content, flags dependent types after confirmed edits, and offers history/recovery. | `modules/research-workflow/final-map.ts`, `workflow-edit.ts`, `versioned-context.ts`, `state-machine.ts`; final-map/history routes |

The methodology was therefore **operationalized across the workflow, data schema, generation instructions, validation functions, persistence and interface**, rather than inserted as a single system prompt. Prompt instructions condition candidate generation and forbid invented references or completed findings, while schemas and server-side checks constrain outputs independently of model compliance. The researcher can edit and confirm the resulting units. The current system has no evidenced dedicated validation stage for secondary research questions, although that stage appears in the v0.1 methodological specification. Its knowledge suggestions and methodology classification should not be described as a self-growing expert knowledge base. The system's AI role is bounded generation and advisory review inside that controlled workflow; it is not autonomous scientific decision-making.

### 4.2 Versioning, provenance and limits

The application separates canonical content from step drafts and AI proposals. A confirmed edit can mark downstream component types `stale`, while the earlier content remains available for inspection. Version history records units and actions, and restoration returns an earlier unit as an editable draft in the current context. Explicit component links and reference identifiers support inspection of the map, but the presence of a link or source does not establish that the underlying scientific claim is justified. A final coherence review can provide suggestions; completion can remain possible with academic warnings. The article must show this behavior, including negative cases, rather than presenting completion as a scientific quality certificate.

The implementation uses a state machine, structured generation and persistent records. Its exact provider configuration, model versions, code revision and runtime settings must be frozen and reported with the benchmark. The evaluated evidence currently includes local tests of SQL, route handlers and export functions in separate layers. It does not yet establish a complete authenticated HTTP-to-database journey or user-level benefit.
